# vLLM patches for the Qwen3.8-27B deployment

**These patches are now commits on this branch.** `qwen3.8-27B` is upstream
`acb0f1dcd` (`vllm 0.27.2rc1.dev110+gacb0f1dcd`) with the eleven changes below
applied in order, so the deployment installs directly:

```bash
VLLM_USE_PRECOMPILED=1 uv pip install git+https://github.com/gabewillen/vllm@qwen3.8-27B
```

No venv-local patching and no lane branches are needed. The patch files and
`apply-to-venv.sh` are kept for reference and for porting onto a different
upstream base.

The rest of this file documents what each change does and why.

---


None of these eleven changes is in any vLLM release. Installing this branch
carries all of them. If you instead run a stock wheel in a venv, apply them
with `apply-to-venv.sh` after every venv rebuild, which silently drops them.

(a) **Telemetry** - per-request normalised entropy, top1-top2 margin and p(`</think>`) at the canonical stage (after penalties, before budget force/temperature/top-k/p), committed rows only, both runners, opt-in per request via `vllm_xargs.effort_telemetry`, JSONL sink `VLLM_EFFORT_TELEMETRY=/path` with per-step rows and one `event: finish` record per request carrying `requested_effort` (as sent, `null` when omitted), `effective_effort` (served), token counts, `finish_reason` and the dynamic report; zero work when no request is flagged. (b) **`reasoning_effort: "dynamic"`** - one effort *level* per request, decided before the model thinks and rendered as that level's sentence at the true tail of the prompt. Two-phase prefill: the frontend renders one prompt per level and ships the longest common token prefix minus one as the body plus one tail per level; the scheduler caps the first chunk at the body (quantised to a KV block), asks the V2 worker for the body's last hidden row, and queries an online memory (`effort_memory.py`: FIFO ring of L2-normalised pooled states inserted at request finish, valued by the reasoning tokens spent **only at a natural close**; cosine kNN-16, novelty = (1 - max cos)/2, spread = weighted stdev of the neighbours' values; persisted as fp16 `.npz`, warmed at start). An asymmetric map over running t-digests picks the level: `q >= q_high` -> top, `q >= q_mid` -> middle, and only the *downward* band is gated on novelty and spread. **Nothing touches the think block**: a dynamic request sets no thinking budget, no cap, no forced close, no mid-generation escalation; the model ends its own reasoning, bounded only by the client's `max_tokens` and timeouts (`close_kind` natural / client-limit). Cost: one extra engine step per dynamic request; the body is byte-identical across levels so the prefix cache holds one body per conversation. Needs the V2 model runner for the hidden-row capture (V1 profiles log a warning and render `default_level`). | Without it: no per-request uncertainty telemetry, `dynamic` is rejected by the template, and an omitted `reasoning_effort` falls through to `xhigh`. History: v1 (rung ladder 1k/4k/16k/64k with mid-generation escalation) and v2 (quantile-rank rule, soft-limit close, worker-side escalation) were measured on VulcanBench v3 and removed on 2026-08-21; v3 measured 12.3 % of natural closes under-provisioned by the v1 start rung with p90 1 471 think tokens wanted (§13.5) while the label-free kNN separates them at AUC 0.850 out of fold. | 0015 v1/core/{single_type_kv_cache_manager.py, kv_cache_coordinator.py, kv_cache_manager.py}, v1/core/sched/{output.py, scheduler.py}, v1/worker/{block_table.py, gpu_model_runner.py}, v1/worker/gpu/{block_table.py, model_runner.py} | **Dynamic Mamba speculative-state reservation.** A Mamba/GDN layer keeps one copy of its recurrent state per verified draft token so a rejected draft can roll back; `MambaManager` reserved `num_speculative_tokens` of those slots per request at first prefill and kept them for the request's whole life. On Qwen3.8-27B one copy is 48 layers x 48x128x128 fp32 = 151 MB, so K=7 meant 9 copies = 1.36 GB per request (~35k attention-token equivalents against a 1.39M-token pool): the latency profile topped out at ~39 concurrent requests and thrashed above (c64: 206 tok/s, 139 preemptions, measured 2026-08-21) even though `num_speculative_tokens_per_batch_size` had already turned drafting off above batch 32 - the schedule was a knob on the proposer that the allocator never saw. | 0016 config/speculative.py, v1/request.py, v1/core/{kv_cache_utils.py, block_pool.py, kv_cache_manager.py}, v1/core/sched/{scheduler.py, async_scheduler.py}, v1/spec_decode/metrics.py, v1/worker/gpu/model_runner.py | **Lazy drafting** (`speculative_config.lazy_draft`, V2 runner). On a step whose batch-size schedule (or adaptive length) asks for zero drafts the V2 runner does not call the speculator at all - no draft prefill over the step's prompt tokens, no draft decode row, no draft lm_head. Measured 2026-08-21 on the INT4 latency profile at c64 (schedule off above 16, 1024-in/1024-out): with the drafter still running at K=0 the server did 786 tok/s, the same server without a speculative config 946 tok/s - a 17% tax for drafts that never happened.
